!# Building a Professional Homelab with Proxmox, Active Directory, CI/CD, and Secure VPN Access

## Introduction

Setting up an advanced homelab is one of the most effective ways to experiment with enterprise architectures without relying on external infrastructure. For systems engineers and developers, having a controlled environment with virtualization, centralized directory services, CI/CD, repositories, collaborative storage, and internal DNS allows replicating real production scenarios.

This article outlines step by step how to build a homelab using recycled hardware or budget servers with second-hand Xeon CPUs and Huananzhi motherboards, deploying Proxmox as the virtualization platform, and setting up the following services:

* Samba Active Directory (AD/DC)
* Jenkins
* GitLab
* Nextcloud
* Nexus Repository
* Pi-hole (DNS and DHCP)
* WireGuard + WireGuard Web UI
* Secure exposure using DuckDNS and port forwarding

The goal is to create a cohesive internal network with private DNS resolution, centralized authentication, and secure remote access via VPN.

---

## General Homelab Architecture

### Base Hardware

The homelab foundation includes:

* Second-hand Xeon CPUs (common E5 v3/v4 models)
* Huananzhi motherboards supporting ECC memory
* 32–64 GB RAM recommended
* SSD storage for VMs
* Additional disk for bulk storage

This setup provides excellent cost-to-performance ratio for virtualization workloads.

### Hypervisor: Proxmox VE

Proxmox offers:

* KVM virtualization
* LXC containers
* Web-based centralized management
* Scheduled backups
* Virtual networks and bridges

Recommended network setup:

* Primary bridge (`vmbr0`) linked to the physical interface
* Optional VLANs for future segmentation

Conceptual diagram:

```
Internet
   |
Router (Port Forwarding)
   |
vmbr0 (Proxmox)
   |--- VM-AD
   |--- VM-GitLab
   |--- VM-Jenkins
   |--- VM-Nextcloud
   |--- VM-Nexus
   |--- VM-Pihole
   |--- VM-WireGuard
```

## Active Directory with Samba AD/DC

### Domain Setup

Samba allows implementing an Active Directory-compatible domain controller.

On a Debian VM:

```bash
apt install samba krb5-config winbind smbclient
samba-tool domain provision --use-rfc2307 --interactive
```

Typical configuration:

* Domain: `lab.local`
* Realm: `LAB.LOCAL`
* Role: DC

Enable service:

```bash
systemctl disable smbd nmbd winbind
systemctl enable samba-ad-dc
systemctl start samba-ad-dc
```

### Benefits in a Homelab

* Centralized authentication
* User and group management
* LDAP integration preparation
* Realistic enterprise environment simulation

## Internal DNS and DHCP with Pi-hole

Pi-hole serves dual purposes:

* Internal DNS server
* Optional DHCP server

### DNS Configuration

Assign static IPs for each service:

| Service   | Internal IP  | DNS Record        |
| --------- | ------------ | ----------------- |
| AD        | 192.168.1.10 | ad.lab.local      |
| GitLab    | 192.168.1.20 | git.lab.local     |
| Jenkins   | 192.168.1.21 | jenkins.lab.local |
| Nexus     | 192.168.1.22 | nexus.lab.local   |
| Nextcloud | 192.168.1.23 | cloud.lab.local   |
| WireGuard | 192.168.1.30 | vpn.lab.local     |

In Pi-hole:

* Add static A records
* Set a local domain
* Point router/DHCP to Pi-hole as primary DNS

### DHCP from Pi-hole

If enabled:

* Disable DHCP on the router
* Configure a range (e.g., 192.168.1.100–192.168.1.200)
* Set gateway and internal DNS

This ensures all devices use the homelab DNS.

## GitLab: Code Management and DevOps

Deploy GitLab using the Omnibus package on a dedicated VM.

```bash
apt install curl openssh-server ca-certificates
curl https://packages.gitlab.com/install/repositories/gitlab/gitlab-ee/script.deb.sh | bash
apt install gitlab-ee
```

Configure:

```
/etc/gitlab/gitlab.rb
external_url "http://git.lab.local"
```

Reconfigure:

```bash
gitlab-ctl reconfigure
```

### Integration

* Internal repositories
* Container registry
* Pipeline management
* Integration with Jenkins

## Jenkins: Internal CI/CD

Deploy Jenkins on a separate VM:

```bash
apt install openjdk-17-jdk
wget -q -O - https://pkg.jenkins.io/debian-stable/jenkins.io.key | apt-key add -
apt install jenkins
```

Access:

```
http://jenkins.lab.local:8080
```

Recommended:

* Integrate with GitLab via webhooks
* Centralize credentials
* Configure agents for distributed builds

## Secure Exposure with DuckDNS and WireGuard

### DuckDNS (DDNS)

Maps a dynamic public IP to a subdomain:

```
myhomelab.duckdns.org
```

Update script:

```bash
echo url="https://www.duckdns.org/update?domains=myhomelab&token=TOKEN&ip=" | curl -k -o ~/duck.log -K -
```

Automate via cron every 5 minutes.

---

### Router Port Forwarding

Only forward:

* UDP 51820 → WireGuard VM

Do not expose GitLab, Jenkins, or AD directly.

---

## WireGuard: Secure VPN Access

WireGuard provides lightweight, high-performance VPN.

### Installation

```bash
apt install wireguard
```

Generate keys:

```bash
wg genkey | tee privatekey | wg pubkey > publickey
```

`/etc/wireguard/wg0.conf`:

```
[Interface]
Address = 10.10.0.1/24
ListenPort = 51820
PrivateKey = SERVER_PRIVATE_KEY

[Peer]
PublicKey = CLIENT_PUBLIC_KEY
AllowedIPs = 10.10.0.2/32
```

Enable forwarding:

```bash
sysctl -w net.ipv4.ip_forward=1
```

### WireGuard Web UI

Provides:

* Peer management
* QR code generation
* Visual client control

Installed as a web service on the WireGuard VM.

---

## Remote Access Flow

1. Client connects to `myhomelab.duckdns.org`
2. Router forwards UDP 51820 → WireGuard VM
3. WireGuard assigns 10.10.0.x IP
4. Client uses internal DNS (Pi-hole)
5. Access internal services:

* git.lab.local
* jenkins.lab.local
* cloud.lab.local
* nexus.lab.local

Remote access behaves as if connected locally.

---

## Security Best Practices

* Never expose web services directly to the Internet
* Limit WireGuard peers
* Regular Proxmox backups
* Snapshots before major changes
* Isolate lab network from home network if possible
